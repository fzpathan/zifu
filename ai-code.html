📦 Project Overview

ai_coding_agent is an AI-powered coding assistant that uses a reactive agentic loop to process user messages and execute tools. It leverages an LLM to understand user intent, decide which tools to use, and generate responses.

Core Components

1. Agent Orchestrator
The Agent class (agent.py) is the core orchestrator. Its run() method is the entry point that handles a single user message.
2. Session Manager
The Session class maintains all state: LLM client, tool registry, context manager, hook system, and configuration.
3. LLM Client
Handles communication with the language model API, supports both streaming and non-streaming responses.
4. Tool Registry
Stores available tools with their schemas, allowing dynamic discovery and invocation.
5. Context Manager
Maintains conversation history, handles message additions, and tracks token usage.
6. Hook System
Triggers callbacks before and after agent runs, enabling extensibility.

🔄 The Agentic Loop

1
Agent.run() Entry Point
Called when a user sends a message. Triggers before_agent hooks, adds message to context, yields agent_start event.
2
Context Compression Check
If tokens exceed 80% of context window, the ChatCompactor summarizes older messages to preserve context space.
3
Get Tool Schemas
Retrieves available tools from the ToolRegistry to send to the LLM.
4
LLM Chat Completion
Sends conversation history and tool schemas to LLM. Collects TEXT_DELTA, TOOL_CALL_COMPLETE, MESSAGE_COMPLETE events.
5
Store Response + Tool Calls
Adds assistant message with response text and tool calls to context.
6
Execute Tools
Non-mutating tools run in parallel, mutating tools run sequentially. Results are added to context.
7
Loop Detection
Checks for repeating patterns. If loop detected, injects a loop-breaker prompt.
8
Prune Tool Outputs
When context exceeds 60% capacity, older tool results are cleared to preserve space.

Async Generator Pattern

The run() method is an async generator — it yields events as they occur, allowing the caller to stream responses in real-time rather than waiting for complete processing.

📡 Non-Streaming Response Handling

The LLM client supports both streaming and non-streaming modes. Both paths converge to the same event types for unified processing.

Streaming vs Non-Streaming Comparison

Aspect Streaming (_stream_response) Non-Streaming (_non_stream_response)
TEXT_DELTA events One per content fragment (token-by-token) Single event with full content
TOOL_CALL events TOOL_CALL_START, multiple DELTA, then COMPLETE Single TOOL_CALL_COMPLETE per tool
Response pattern Real-time incremental display Waits for complete LLM response
Use case Interactive UI with live updates Batch processing, simpler integration

🧠 Context Management

The context manager maintains conversation history using a tiered retrieval system to optimize token usage.

Token Budget Tiers

L0 — Always Included
System prompt + Recent messages within default 20k token budget
L1 — Conditionally Included
Older messages within L0 + L1 budget (+8k tokens), selected by relevance (min score 0.15)
L2 — Archived
Messages beyond L1 budget, never sent to LLM

When context exceeds 80% of the token budget, older messages are summarized:

Key Concepts

AsyncGenerator
A function that is both async and a generator. It can yield multiple values over time, enabling streaming responses as events occur.
Context Window
The maximum number of tokens the LLM can process. When exceeded, context compression summarizes older messages.
Agentic Loop
A pattern where an AI agent repeatedly calls an LLM, processes tool calls, and feeds results back until a final response is produced.
Hook System
A plugin-like system that triggers custom code before and after agent runs. Used for logging, metrics, authentication, etc.
